# Code quality standard

Binding for all code generated by the framework.

## Learner-facing code (educational content)

Binding for every program, lab, tutorial, drill, starter template, and model solution generated for a learner (`mlt-lab`, `mlt-tutorial`, `mlt-drill`, `mlt-mentor` teaching code). The code is itself the teaching material, so:

- **Comment every non-trivial block.** Each function, loop, and mathematical operation carries a comment explaining *what it does and why* — the concept behind the line, not a restatement of the syntax.
- **Explain the math in code.** When a line implements a formula (gradient update, loss, normalization), the comment states the formula in plain notation and maps each symbol to the variable used.
- **Name for teaching.** Prefer descriptive names (`learning_rate`, `predicted`, `squared_error`) over terse ones; if a canonical short name is used (`w`, `b`, `eta`), a comment defines it on first use.
- **Mark the load-bearing lines.** The one or two lines where the concept actually lives get an explicit marker comment (e.g. `# KEY IDEA:`) so the learner can find the essence fast.
- **State expected output near the code** (in comments or the accompanying doc) so the learner can self-verify.
- **No magic numbers.** Every hyperparameter or constant gets an inline justification (why this value, what happens if it changes).
- Framework/maintenance scripts (non-learner-facing) follow the regular sections below without the teaching-comment density.

Example:

```python
# Prediction for every point at once: y_hat = w*x + b (vectorized).
# w*x is the dot product idea from M1 — each input scaled by its weight.
y_hat = w * x + b

# Residuals: how far each prediction is from the truth.
err = y_hat - y

# KEY IDEA: the update step. The gradient points uphill, so we step
# opposite to it: w <- w - eta * dL/dw. eta (learning rate) sizes the step.
w = w - eta * grad_w
```

## Python standards

### Style

- Follow PEP 8 for formatting
- Use type hints for function signatures
- Use f-strings for string formatting
- Prefer pathlib over os.path for file operations
- Use dataclasses or Pydantic for structured data

### Structure

```python
"""Module docstring explaining purpose."""

import standard_lib
import third_party
import local_module

CONSTANT = "value"

def main_function(param: str) -> dict:
    """Docstring explaining what this does."""
    # Implementation
    pass

if __name__ == "__main__":
    main_function("example")
```

### Error handling

- Use specific exception types, not bare `except:`
- Log errors with context (what was attempted, what failed)
- Provide actionable error messages
- Use try/finally for resource cleanup

### ML-specific practices

- Set random seeds for reproducibility:
  ```python
  import torch
  import numpy as np
  import random
  
  torch.manual_seed(42)
  np.random.seed(42)
  random.seed(42)
  ```

- Use configuration files (YAML or JSON) for hyperparameters
- Save checkpoints during training
- Log metrics to TensorBoard or Weights & Biases (offline/local mode — no cloud sync by default)
- Use `torch.no_grad()` for inference
- Use `model.eval()` and `model.train()` appropriately

## Jupyter notebooks

- Clear all outputs before sharing
- Number cells logically
- Include markdown cells explaining each section
- Make cells idempotent (can run multiple times)
- Put imports in the first cell

## Testing

- Include at least one test or validation for every function
- Use assertions to check expected behavior
- Test edge cases and error conditions
- For ML: validate model outputs, not just code execution

## Documentation

- Every function needs a docstring
- Include: purpose, parameters, return value, example usage
- Use Google or NumPy docstring format consistently

## Version control

- Small, atomic commits
- Descriptive commit messages
- No credentials, API keys, or large files in git
- Use .gitignore for models, datasets, and cache

## Dependencies

- Pin major versions in requirements.txt
- Use virtual environments
- Document why each dependency is needed
- Prefer actively maintained libraries

## Forbidden patterns

- Hardcoded paths without configuration
- Global mutable state
- Print statements instead of logging
- Bare `except:` clauses
- Ignoring return values
- Magic numbers without explanation
- Copy-pasted code without refactoring
